# 将游戏参考转成实现条件

针对 GPT-6 Astra 在奥日案例中出现的参考错认、观察不充分和实现偏离，先把可见证据变成开发约束。不要把这些现象归因于未经验证的训练数据，也不以其他模型“看过更多素材”作为结论。

**参考不是一组装饰性链接。每个关键实现决定应能指出依据的画面、观察结果与验收方法。**

## 1. 先明确要研究的对象

读取用户提供的文件、现有游戏和已有研究记录，再决定是否补搜。记录作品 / 版本、具体角色、关卡或环境、技能形态、相机类型以及用户需要对齐的部分。

- 同系列不同作品、普通技能与升级技能、普通下落与下砸攻击分别标记。
- 区分“复现可见体验”“借鉴风格”和“使用原始资产”；三者需要的证据和实现方式不同。
- 检查现有玩法是否与用户最新要求一致，不能拿旧版近战测试证明新版远程攻击完成。
- 若只有某一局部待修，聚焦这个局部和相关切换，不重新研究整个游戏。

为本轮列出少量明确观察问题。例如：“下降中段双手在肩膀哪一侧？”“释放时世界画面是否缩小？”“暖光是否照到了可行走顶面？”

## 2. 按问题寻找足够的素材

已有素材能回答问题就直接使用。需要网络参考时，优先搜索：

1. 官方成品游戏视频或可确认版本的高清实机。
2. 原动画师、环境美术师或技术美术师的作品展示与说明。
3. 能明确辨识对象、动作和版本的其他实机视频。

检索组合使用作品名、角色 / 技能名与观察目标，例如 gameplay close-up、animation reel、environment lighting。检索技术实现时优先引擎官方文档或原作者说明。

创作者 reel 可能包含测试或未采用片段，适合观察形体与动作关系；最终节奏仍与成品游戏交叉核对。增强技能、MOD、剪辑变速与调色画面不能默认代表基础版本。

达到“对象可确认、目标过程可见、关键差异可判断”即可开始实现。只有未解决的问题阻碍设计时再补搜，不把堆链接当作进度。

网络不可用或用户要求离线时，使用已有材料并标注缺口。不能假装观看了无法访问的视频；在缺失信息不阻碍的部分继续工作。

## 3. 真正查看并核实身份

打开视频或可访问预览，查看代表性原帧。不可仅凭搜索标题、缩略图、文件名或页面描述判定主角身份。

记录能确认身份的可见线索，例如头身比例、耳部、服饰、武器、UI 与所在场景。遇到 NPC、敌人或其他作品角色，明确排除。

奥日案例曾误把非目标角色的图片当作建模依据。纠正方式是重新查看实际帧，核实白色长耳主角，再做局部裁图；不能继续在错参考上细化模型。

## 4. 同时保留全画面和局部裁图

对合法可访问的素材，使用环境支持的预览或提帧工具：

- 保留原始时间戳、分辨率、帧率，以及是否发生剪辑或变速。
- 全画面用于判断镜头、背景尺度、构图、光源与地面关系。
- 主角裁图用于比较轮廓、关节、手足、武器和耳尾；保留必要的接触环境。
- 动态裁切应记录跟踪位置，避免把裁剪移动误认为主角或相机运动。
- 等比例放大可以帮助观察像素，不产生新的可信细节。不要用生成式补帧或增强后的虚构细节测量原始关节轨迹。
- 正常速度看节奏，慢放看路径，接触表看阶段。三者用途不同。

可以围绕事件加密取帧，而非只按等间隔截出大量重复帧。最少覆盖事件前、发生时和结束后；关节与动作分析还需覆盖完整周期。

无法直接提取时使用可用预览并如实记录精度限制，不绕过访问限制。网络参考用于分析不等于可以直接打包原资产；需要实际复用时核对许可与项目授权。

## 5. 把观察写成可操作的约束

为关键证据填写参考卡，不要求每张截图都产生一份冗长报告：

~~~yaml
id: jump-descent-01
source: 用户提供的游戏片段
identity: 已查看原帧并确认目标角色
segment: 顶点之后至首次接地之前
artifacts: 全画面、主角裁图、阶段接触表
observed: 下降时一腿伸展一腿屈曲，双手向外而非贴脸
inferred: 可用分阶段 pose 权重与次级惯性重建
unknown: 原始骨架、精确动画曲线
implementation: 下落姿态层；不改既有重力和跳跃高度
acceptance: 同阶段近景对照及正常速度短跳、高跌落连续播放
confidence: 对可见轮廓高，对原始参数低
~~~

其中时间、路径和数值应填实际信息；以上是字段示例。把“看到什么”和“准备用什么实现”分开，不能从单张截图断言原游戏一定采用某种 shader 或骨骼算法。

### 按观察对象建立对应表

| 对象 | 提取内容 | 应映射到的实现决定 |
| --- | --- | --- |
| 建模 | 比例、剪影、关节厚度、体块过渡 | 拓扑、连续曲面、截面和材质层次 |
| 动画 | 阶段、接触、重心、领先 / 滞后部位 | 动作层、曲线、IK 目标与中断规则 |
| 色彩 | 区域、明暗分组、局部光核与承光面 | 分区 recipe、光照、材质、雾 |
| 特效 | 形状、方向、层次、寿命与事件先后 | 发射器、曲线、碰撞回调、合成 |
| 镜头 | 静物屏幕尺度、焦点、跟随与恢复 | zoom / FOV 曲线、目标与安全框 |
| 玩法 | 输入、反馈、释放、命中和恢复 | 状态机、输入响应、伤害与演示路线 |

测量角色比例时保持宽高比，可用头宽或角色高度归一化，并注明姿态、透视和遮挡。对动作时序同时保留实际时间与归一化阶段；时间重对齐不能被用来掩盖节奏误差。

## 6. 处理冲突与不确定性

- 用户选择的玩法是目标；参考视频用于理解细节，不覆盖用户的新要求。
- 同一技能存在多个版本时，注明采用哪一个及原因。远程单箭的任务不能无意复制强化三箭，也不能拿光刃片段解释拉弓。
- 只看到效果时，允许选择效果等价的技术近似，但说明是推断。例如观察到景深不等于掌握原作景深参数。
- 没有对应关卡参考时留空或标为原创延展，不拼一张别处图片伪称同场景。
- 来源发生冲突且影响关键设计时补充一条能区分的证据；仍不能判断时明确假设，不制造精确结论。

## 7. 在实现与 critic 之间维持证据链

让每项关键改动引用参考卡 ID，验收时同时展示参考、修改前和当前实际输出。统一观看尺度、动作阶段和渲染条件；相机不同的画面比较视觉关系，不强求像素重合。

为 subagent 提供原素材位置、裁图、观察结论、目标要求与未知项。仅发一句“像奥日”“参考这个链接”不构成可执行任务。

主 critic 必须亲自查看关键证据，不把 subagent 的描述当作原画面。发现错参考时撤回受影响的结论，保留与该错误无关的已通过工作。

## 完成条件与交付

- 目标对象与技能形态已核实，关键过程实际可见。
- 至少有能解释当前缺陷的参考 / 当前对照，且出处和时间可追溯。
- 观察已转化为实施任务与可观察的验收条件。
- 未知项与推导参数明确；没有伪称官方 recipe、原骨骼或完整复原。

交付精简的参考清单、关键裁图 / 接触表、约束表和仍需确认的细节；不交付一堆未经查看的链接。

奥日案例的迁移价值在于“参考成为开发条件”：先核实是谁、处于什么动作和哪个环境，再把可见差异落实到造型、事件、镜头和色彩，而不是依赖模型对作品的模糊记忆。
