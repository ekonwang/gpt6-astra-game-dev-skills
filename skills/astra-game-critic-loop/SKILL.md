# 主 agent 与 subagents 的 critic 迭代

面向 GPT-6 Astra，防止把“写完代码”“子代理说完成”“测试数量很多”误判为目标已经达成。主 agent 对最终体验与交付负责，subagent 对明确边界内的实现负责。

本工作流使用可用的多代理能力分工；继承当前已选模型，用户另有指定时遵循其选择，不为执行 skill 擅自修改全局模型设置。没有 subagent 工具时可以串行分开实现与复审，但如实说明没有完成独立代理审查。

**严厉的 critic 必须指出可复现的差距、证据与通过条件。严厉不等于贬低实现者、扩大范围或无限追求更多功能。**

## 1. 先把目标状态写具体

读取用户最新要求、现有实现和可用参考，形成一份与任务规模相称的验收约定。至少区分：

- **玩法**：玩家怎么触发、得到什么反馈、结果怎样发生。
- **视觉**：轮廓、动作阶段、颜色、空间层次和关键特效。
- **完整性**：输入切换、中断、暂停、失败 / 重生、连续触发与演示。
- **运行约束**：目标设备、版本、文件形式、离线要求和性能预算。

“100% 复刻”“艺术品级”“足够顺滑”不能单独成为验收条件。将其拆成具体可见、可操作的目标；没有原资产、骨骼或参数时，不承诺无法验证的逐像素或逐帧一致。

~~~text
任务：修复蓄力镜头与瞄准提示
参考：已核实的视频时间段、全画面和局部裁图
当前缺陷：自动演示同一步开始并释放，箭头没有展示帧；背景尺度不变
目标状态：瞄准阶段可读；背景逐步放大；释放瞬间回缩并平滑恢复
保持：玩家即时转向与释放；已通过的弹射轨迹、碰撞和输入
验收：真实输入 + 自动路线连续播放；静物屏幕尺度；各方向与目标宽高比
交付：改动文件、实际产物标识、视频 / 截图、行为结果、仍存在的差距
~~~

阈值来自用户约束、参考或明确说明的工程选择；先定义再验收。发现测试方法有错可以修正，但必须保留原因与旧结果，不能为了通过降低目标。

若用户明确要求使用 goal 工具，才将上述目标状态写入 goal；不要仅因本 skill 提到 goal 就创建。只有实际要求完成才能标记完成，不能把预算耗尽等同于达标。

## 2. 按独立问题分工并确定交接

主 agent 负责目标、集成、证据复核与最终裁决。按规模选择少量实现 subagents；重大视觉或行为变化可另给独立 critic 做有范围的复审。

适合分开的例子：

| 分工 | 实现职责 | 需要与其他分工明确的接口 |
| --- | --- | --- |
| 角色与动作 | 模型、IK、动作阶段与接触 | 武器挂点、瞄准坐标、事件时间 |
| 环境与配色 | 光照、材质、雾与空间层次 | 玩法焦面、遮挡规则、保护对象 |
| 技能与镜头 | 发射、效果、提示、相机曲线 | 输入、碰撞、最终方向、暂停时钟 |
| 独立 critic | 指定风险的观察与验证 | 被测版本、真实入口、证据口径 |

分工按耦合程度调整，不机械地每个文件一个 agent。共享文件指定单一写入者；使用隔离分支 / worktree 或约定补丁接口，不能让多个代理覆盖同一份文件。

单文件 HTML 交付可以保留模块化开发源，由一个集成者生成最终文件。各代理的临时 HTML 仅用于专项验证，不能分别替换最终产物。

性能测量或大型渲染需要独占设备时串行安排，避免多个浏览器争用 GPU 后得出错误比较。普通独立阅读与实现可以并行。

## 3. 给 subagent 可执行的任务单

每个任务单包含以下必要信息：

~~~text
负责的问题与原因：
可修改的文件 / 接口：
必须保持的行为与已通过部分：
参考位置、身份确认、时间段与关键观察：
具体目标状态：
验收方法、阈值及其依据：
需返回的证据与产物版本：
已知依赖、禁止并行写入的部分：
~~~

对问题指明症状和目标，不预先锁死缺少证据的技术方案。要求 subagent 先确认根因，再提交实现和自检结果。

subagent 只能提交“候选实现”与其证据，不能替主 agent 宣布整体交付通过。发现依赖阻碍时应说明事实和可继续推进的部分，不虚报完成。

## 4. 主 critic 亲自检查候选

先确认实际产物与报告一致，再按要求审查。不要把子代理的解释当作画面本身。

| 审查方式 | 能证明什么 | 不能替代什么 |
| --- | --- | --- |
| 代码与接口检查 | 实现路径、状态归属、依赖与潜在缺陷 | 实际画面和手感 |
| 数值 / 行为检查 | 输入、碰撞、接触、时钟和状态不变量 | 美术风格达标 |
| 灰材质 / 同机位对照 | 轮廓、变形、明暗和局部差异 | 正常速度的整体节奏 |
| 连续游戏片段 | 动作衔接、可读性、镜头与音画关系 | 边界状态的完整覆盖 |
| 实际玩家输入 | 操作入口与响应 | 自动演示是否展示目标内容 |
| 自动路线 | 演示过程与完整性 | 玩家输入和目标机制的因果正确性 |

根据改动选必要方法，不要求每个小修复都执行全套。需要视觉结论时必须真正查看图片或视频；无法查看就标为未验证，不补写想象中的观感。

检查“结果发生的原因”：

- 远程战斗演示通关，还要确认伤害来自远程弹体，不能主要靠踩头。
- 箭头对象存在，还要确认观众实际看到足够的瞄准过程。
- 镜头参数变了，还要确认场景静物的屏幕尺度确实变化。
- 景深指标改善，还要确认细弓弦与箭尾没有变成采样重影。
- 平台统计更亮，还要确认亮的是可见顶面，不是喷涂崖肩。

## 5. 用明确 feedback 退回，实现乒乓迭代

每轮优先处理最影响当前目标的少量问题。已通过的部分明确保留，避免返工演变成整场重写。

~~~text
结论：退回 / 局部通过 / 通过
问题 ID 与严重程度：
证据：产物版本、片段时间、截图区域、复现步骤
观察到的差距：
为什么影响已约定目标：
下一轮修正方向：
保持不变的部分：
再次验收方法：
~~~

有效反馈：“R3 暖林右侧平台正面出现连续金褐光斑，真实土苔顶面仍暗。主要承光移到实际朝上的可见表面，按纹理打断；保留 R2 天空与景深。提交同机位全图、缩略图和局部顶面对照。”

无效反馈：“感觉还是不高级，再多优化一点。”

返修可以交回原 subagent 保持上下文；若同一缺陷反复出现、根因判断停滞或方案明显陷入局部修补，交给新的 subagent：

- 提供最小必要的原始参考、当前候选、验收约定与已确认的失败事实。
- 要求重新诊断根因并提出不同的可验证修正，不仅调整旧参数。
- 如需独立判断，先提供任务、参考与当前产物，让新 critic 独立查看，再与原反馈交叉核对。
- 明确新旧文件写入者，避免两个代理同时修同一缺陷。

连续两轮同一问题没有可观察改善时，优先重新审查参考、指标、接口或技术路线，再决定替换执行者；不是自动接受，也不是不停增加代理。外部素材或能力确实缺失且阻碍目标时说明缺口，只就关键决策向用户提问，同时完成不受阻的部分。

## 6. 接受之后冻结范围，再联合验收

满足约定目标且无阻挡问题即可通过；不以“必须迭代几轮”或“必须耗满若干小时”作为成果。用户提出新要求时重新打开受影响部分，保留仍有效的通过结论。

集成后检查：

1. 统一构建实际交付，记录文件 SHA-256，或多文件构建的版本 / 清单。
2. 在该产物上复测受集成影响的行为、视觉与运行入口，不能把不同临时版本的通过项相加成“最终全部通过”。
3. 检查跨模块边界：动作与武器坐标、最终瞄准与残光、暂停与相机、透明效果与 DOF、重生与镜头。
4. 用自然操作或真实自动路线完成关键体验，不用传送、无敌或跳过路线代替最终试玩。专用测试夹具可用于隔离问题，但标明用途。
5. 有性能要求时在独立正常运行中测量；离线确定性录像的生成速度不是游戏帧率。
6. 若交付视频要求声音，验证实际音轨与同步；若要求部署，按已有授权部署并核对实际地址与访问范围。

后续修改使证据失效时，重跑受影响的检查。已有检查已通过且没有新风险时，进入交付，不为凑数量重复跑测试。

## 7. 如实报告结果、差距与投入

主 agent 最终说明已实现什么、用什么证据接受、在哪些环境验证，以及仍存在的具体差异。内部评分可以辅助排序，但不给无依据的“99% 还原”。

需要统计 agent 投入时区分：

- 墙钟时间：整项任务从开始到结束的实际跨度，注明是否包含等待。
- 主 / 子代理执行时间：按实际记录分别相加，并说明并行部分会重叠。
- 费用或计算消耗：只有真实计量数据才能报告，不能由执行时长推算。

不把多代理累计时间当作用户实际等待时长，也不把很长的投入当作美术质量证明。

## 奥日案例提炼的停止与退回规则

- 几何、相机和箭头各自通过后，联合画面仍可能被前景遮挡；需要集成复查。
- 远程演示经过多轮通关仍因踩头杀敌被退回，直到实际伤害来源符合要求。
- 亮度数值改善曾被真实画面的灯带与错位受光否决；定量结果不能压过目标本身。
- 临时包修改景深后，旧报告不能冒充新包证据；最终验收绑定统一交付。

把这些经验用于新的游戏时，迁移的是“目标—实现—证据—反馈—返修”的闭环，不是奥日的参数、固定代理数量或十小时工期。
