# 有机建模与动作变形

为 GPT-6 Astra 设置明确的造型与动作验收门槛。这里针对的是奥日案例中观察到的交付问题，不假设模型的训练数据或内部原因。可用于其他角色、怪物、植被和有机地形；沿用项目引擎。

**完成信号是轮廓、变形和接触在实际游戏中成立。几何体数量、三角形数量与代码复杂度都不是完成信号。**

## 开始前锁定目标

读取现有模型、动画、碰撞与构建入口，保存当前版本和代表性画面。按任务规模记录以下内容，已有资料直接复用：

| 项目 | 需要明确的内容 |
| --- | --- |
| 视觉对象 | 具体角色或部位；已核实身份的参考与时间段 |
| 观看条件 | 实际游玩相机、角色屏幕高度、最近展示距离、目标设备 |
| 风格 | 有机连续曲面、刻意低模、机械装甲或其他选定风格 |
| 动作范围 | 本次涉及的动作及相邻切换；关键支撑点、抓握点 |
| 允许修改 | 模型、骨架、动画、物理分别可改到哪里 |
| 成本 | 现有帧耗时、可接受增量、资源大小或离线约束 |

缺少不影响推进的信息时先按现有游戏设定工作。若只要求改善动作，不顺带改变跳跃高度、移速、碰撞盒或关卡难度。

## 1. 将“僵硬”拆成可定位的问题

先看正常速度片段，再看慢放和关键帧。分别判断：

- **造型问题**：体块比例、轮廓、关节外露、均匀圆管、突变粗细、肩髋接缝。
- **变形问题**：弯曲处塌陷、伸展变细、扭转翻面、法线断层、皮肤与骨架脱离。
- **时序问题**：姿势正确但进入太晚、恢复太早、整条肢体同步运动、弹簧追不上步态。
- **接触问题**：滑步、脚趾穿地、手掌与武器分离、落地准备早于可落平台。

为每个待修问题提供参考裁图、当前裁图、动作阶段和可见差异。不可用“更自然”“多加细节”作为唯一实现要求。

## 2. 先改体块与轮廓，再分配 triangles

1. 用无自发光的中性材质检查头、胸、腹、骨盆、四肢比例；同时保留正常材质截图。低发光审查用于暴露缺陷，不改变最终美术目标。
2. 在实际游玩尺度和近景尺度分别检查。先纠正屏幕上可见的轮廓，再处理表面细节。
3. 将面数投入曲率变化、轮廓边缘和关节弯曲区；平坦区与不可见内部避免均匀细分。法线贴图不能修复错误轮廓。
4. 根据近景误差和设备预算选择细分密度与 LOD。没有适用于所有游戏的最低三角形数；数十个独立球体也不等于连续身体。

对柔软角色，可选择已有资产的拓扑修整、蒙皮网格、截面扫掠或其他适合项目的方式，不为程序生成而放弃更合适的资产流程。

### 程序化连续曲面的可用做法

- 用肩—肘—腕、髋—膝—踝的中心线与变化截面构造皮肤。大腿、膝、胫骨、踝、足背各有体积关系，避免仅把圆柱切成更多段。
- 截面点可写为 P(s,θ) = C(s) + U(s)·rx(s)·cosθ + V(s)·ry(s)·sinθ。C 是中心线，U/V 是稳定的局部截面轴；半径、偏心与截面旋转随部位变化。
- 中心线使用平滑弧线，采用平行传输或等价的稳定标架，防止直线附近、曲率反转或左右镜像时截面突然翻转。
- 根部与躯干的可见轮廓连续；内部交叠可按成本处理，不能留下可见肩洞、关节球或靠辉光遮住接缝。
- 把手足作为有掌面、脚背和接触面的体块；只有近景确实可见时再分出指趾。
- 变形后更新必要的法线和包围体；复用顶点缓冲，避免每帧新建整套几何。对动态边界设置有效保守范围或按实际需求重算，防止肢体伸出后被剔除。

采用蒙皮时，检查关节附近的拓扑、权重过渡和体积保持；必要时使用姿态修正形变。更高细分不能补救错误权重。

Three.js 中几何缓冲可用 [BufferGeometry](https://threejs.org/docs/pages/BufferGeometry.html)，骨骼变形可用带有效骨架、蒙皮索引和权重的 [SkinnedMesh](https://threejs.org/docs/pages/SkinnedMesh.html)。具体 API 按项目锁定版本核对，不能直接混用在线最新版。

## 3. 让动作成为分阶段的受力过程

先从参考建立姿态和事件表，再调整曲线。阶段由游戏状态和事件驱动，不依靠一个全局正弦同时摆动全身。

| 动作 | 重点观察与实现 |
| --- | --- |
| 奔跑 | 支撑、蹬地、回收、摆腿；胸肩领前与骨盆跟随；脚接地期间的稳定性 |
| 静止 / 休息 | 重心落在哪里；坐下、坐稳、起身如何衔接；呼吸只作次级变化 |
| 跳跃 / 下落 | 起跳伸展、顶点收身、下降展开、快速下坠、真实落点前的预备 |
| 落地 | 接触、胸胯压缩、吸收冲量、恢复或接入奔跑；不能只有一帧姿势 |
| 攻击 / 技能 | 预备、释放、跟随、恢复；手、武器、发射点与瞄准方向同源 |

- 身体、头、四肢、耳尾设置不同的幅度和响应，次级运动由加速度、受力方向与接触变化驱动；不在普通下落时叠加无依据的踏步循环。
- 动作平滑使用适应时间步长的方法；弹簧需稳定积分或子步处理。不可用固定每帧插值系数让 30 / 60 / 120 Hz 呈现不同动作。
- 检查过渡的相位与响应延迟：过慢的跟随会让后摆手一直弯在肩旁，过短的落地脉冲会在身体尚未压低时消失。
- 普通下落、攻击、冲刺、受击、抓取等的覆盖优先级写清楚；必要时上下身分层。中断、暂停、重生不能保留旧姿态权重。
- 预落地基于有效碰撞平台和实际运动预测；深渊、不可落表面和正在穿过的单向平台不得触发。
- 输入响应、跳跃弧线与动画时间分别检查。不能为了让录像姿势好看而偷偷改变玩家的操作手感。

## 4. 验收连续动作与实际接触

按任务选择必要检查；以下三类证据不能互相替代：

1. **视觉证据**：同阶段的参考 / 修改前 / 修改后；中性材质近景、正常游戏视角、完整周期连续播放。镜像角色还要看另一朝向。
2. **几何证据**：读取变形后、转换到世界坐标的真实皮肤或代表性表面点；检测脚掌、脚趾、坐姿接触和握持位置。骨骼点正确不代表皮肤没穿地。
3. **行为证据**：动作切换、多帧率、暂停恢复、快速反向，以及本次可能影响的跳跃、攻击或技能组合。优先检查真实输入触发的路径。

接触容差应在修改前按角色尺度、碰撞余量和屏幕误差说明。若暂以 1–2 个屏幕像素作为可见滑移诊断，应注明分辨率与机位；它不是所有游戏的统一门槛。

记录实际三角形、绘制调用与帧耗时的变化。保持当前目标设备上的预算；不得仅凭高配开发机流畅就承诺低端设备表现。

## Critic 退回条件

- 关闭辉光后仍是细杆、外露关节球或弯折水管，且与目标风格不符。
- 只改静态造型，完整周期仍滑步、僵直或切换跳变。
- 手腕与武器分别计算导致松脱；检查只看骨骼，没有看渲染表面。
- 面数增加，但轮廓、变形或屏幕效果没有可指出的改善。
- 用抬高地形、修改碰撞或延迟输入掩盖本次动画问题。

反馈示例：“下降中段前手仍贴近嘴部，形成端杯轮廓。把外展路径移到肩以下，保留已通过的双腿错开；提交同一跳跃阶段的近景与正常速度片段，并复查空中瞄准。”

## 交付

提交实际实现、前后对照、相关回归结果、预算变化和仍存在的差异，标明所检验的版本。无原始骨骼或动画曲线时，使用“基于参考重建”，不声称逐帧完全复刻。

奥日案例的可迁移经验：连续截面改善了腿部轮廓，但摆臂还需要单独修正 IK 目标与跟随延迟；脚趾穿地只有真实顶点检查发现。将“造型—时序—接触”作为三个独立验收维度。
