# 配色、明暗与场景美术对齐

面向 GPT-6 Astra 在奥日案例中出现的惯性青雾、均匀发光与偏淡画面设置纠偏步骤。迁移到新游戏时重新取参考，不把这个案例的色板当作通用审美。

**目标是最终画面的色彩关系、光落点与可玩性。材质 HEX 相同、平均亮度提高或换了一层滤镜，都不足以证明风格对齐。**

## 1. 明确这一幕的视觉目标

优先使用已核实的用户素材、成品游戏片段和创作者资料。按区域分别记录：

- 情绪与时间：温暖、肃静、危险、干燥、潮湿等需要画面支持的特征。
- 前景遮框、中景可玩区、远景空气、主光源、角色与交互物各自的作用。
- 目标参考、时间戳、取样区域，以及哪些是观察、哪些是实现推断。
- 必须保持的角色 / 敌人 / 落点 / 危险物可读性和现有性能约束。

先写 3–5 条能从画面判断的要求。例如：“主光为局部琥珀开口；近景保持红褐暗体；下一落脚面承接同一方向暖光；角色与危险物在缩略图中仍能区分。”避免只写“电影感”“高级”“鲜艳”。

如果用户要求其他色系，不用蓝绿色雾、冷色轮廓光和青色粒子把全局重新染回原来的习惯色。若参考本来是青绿色，则保留该方向并修正层次，不能机械禁用青绿。

## 2. 制作按视觉作用划分的 recipe

不用全图平均颜色代替局部设计。选择有代表性的截图，在稳定区域采样，避免字幕、HUD、压缩边缘和瞬时白闪。

| 字段 | 记录内容 |
| --- | --- |
| reference | 来源、片段时间、裁图及采样区域 |
| region / role | 场景区域、前景暗框、中景主体、空气、光核或功能提示 |
| screen_color | 屏幕色块或色簇范围；注明 sRGB / HDR 转换情况 |
| value / chroma | 明暗排序、饱和度关系；必要时附局部统计 |
| coverage | 亮区、暗区的大致空间位置与面积关系 |
| implementation | 材质底色、受光、雾、发光或后处理如何协作 |
| invariant | 不允许丢失的纹理、暗部、路线或角色轮廓 |

屏幕色是整个渲染链的结果，不能直接作为材质输入后声称一致。来源没有官方参数时，明确标注“根据画面推导的 recipe”，不要冠以“官方配方”。

### 奥日案例中的示例，仅供理解方法

| 画面职责 | 暖林屏幕取样 | 洞穴屏幕取样 |
| --- | --- | --- |
| 前景暗框 | #0e0707，红褐近黑 | #050505，近黑 |
| 中景主体 | #5d2714，红褐树干 | #2a5923，受光绿叶 |
| 空气 / 阴隙 | #c25f40，桃橙空气 | #163a1e，深绿间隔 |
| 局部亮核 | #f69657，杏金光隙 | #d1e572，黄绿光井 |

这些值来自特定视频截图的局部取样，不是原作材质数据，也不适用于所有奥日关卡。迁移到沙漠、雪原、赛博城市或像素游戏时，重新建立角色关系和取样表。

## 3. 先诊断渲染链，再调整美术

检查项目锁定的引擎版本、颜色空间、曝光、tone mapping、雾和后处理顺序。优先排除转换缺失或重复；不能用增加灯光补偿错误的输出链。

在 Three.js 路径中：

- 核对颜色纹理、数据纹理与顶点颜色的输入约定；光照运算保持在线性工作空间。
- 最终显示采用正确的输出变换。Composer / 自定义后处理应明确哪一处负责 tone mapping 与输出颜色转换，避免漏做或重复做。
- 自定义 ShaderMaterial 需按实际输出路径处理颜色，不能把适用于直接输出的 shader chunk 盲目加到每个中间 pass。

依据 [Three.js Color Management](https://threejs.org/manual/pages/color-management.html) 核对这些环节，具体属性按项目版本确认。美术修正不要求顺便升级引擎。

## 4. 按问题选择修改，避免盲目增亮

| 观察到的问题 | 优先检查与调整 | 容易产生的次生问题 |
| --- | --- | --- |
| 全图灰淡 | 雾覆盖、环境光、黑位、色彩转换、明暗分组 | 再加饱和度得到脏色 |
| 整体偏暗但局部应有亮感 | 主光面积、亮核、实际受光表面、局部对比 | 全屏曝光抹平暗体 |
| 颜色亮而泛白 | 高光压缩、辉光覆盖、过强自发光、雾色 | 用更浓输入色硬顶造成其他区域过饱和 |
| 青绿占满所有层次 | 是否把同一色赋给雾、环境、粒子和材质 | 换成全局紫色仍然单调 |
| 光源很亮但路线很暗 | 光是否落到实际可见台顶、土苔与邻近物体 | 把崖壁喷成发光灯带 |
| 植物像荧光塑料 | 叶尖、叶面、茎、背光面是否同强度 | 一刀切变暗又失去生机 |

推荐从大关系到小细节推进：灰度分组 → 主辅色 → 光源形状 → 实体受光 → 材质变化 → 适量后处理。一次主要修改一个因果链，保留已经通过的区域。

### 光源必须与场景实体发生关系

- 主光有位置、方向、范围和衰减；光井有局部亮核与断续密度，不做等宽贯穿整幕的白墙。
- 检查真正被渲染的上表面，不能只给预想中的苔藓层加光。倒角或覆盖网格可能才是玩家看见的表面。
- 受光由表面朝向、纹理和位置共同调制；保留岩缝、土块和背光面，不用平滑自发光色斑覆盖材质。
- 需要限制照亮范围时结合空间位置与场景语义；仅按法线朝上会把崖壁下方的岩凸也照亮。
- 让相邻落点、交互物和环境光形成可读关系。不要为了构图把前景枝干移入操作视线。

## 5. 用固定条件的画面对照验收

保存参考 / 修改前 / 修改后，固定机位、时间、分辨率与随机种子。参考地形不同时，比较等价视觉作用，禁止拉伸画面或扭曲构图来制造像素一致。

每次检查：

1. 正常全图：光源、材质、角色与路线是否协调。
2. 缩略图：缩至约 320 像素宽或相近观看尺度，主次与路线是否仍成立。
3. 灰度图：暗框、中景与亮核是否分离；不是单纯看全图平均值。
4. 局部近景：纹理是否被乳白辉光、荧光草或喷涂光斑抹掉。
5. 移动镜头：区域过渡、遮挡、曝光或雾色是否跳变；关键战斗时仍可读。

统计仅用于定位问题。可以报告指定区域的中位数、亮部百分位、亮像素面积或色簇，但写明阈值和色彩口径。直接对编码后的 sRGB 通道加权得到的是显示值指标，不称物理亮度；需要线性相对亮度时先正确解码。

不强求不同构图的直方图相等，不用统计改善覆盖目视失败。比如台肩亮度上升但真实台顶仍暗，应退回受光落点问题。

## Critic 退回条件

- 用户指定的新色系仅存在于色板，最终画面仍被统一青雾覆盖。
- 全局更亮，但暗部消失、亮核发白或场景层次变少。
- 天空光改善，地表仍不承光，或出现连续发光崖肩。
- 只给参数与色值，没有最终渲染；只给最好看的一幕，其他区域退化。
- 将取样近似写成官方参数，或用一个色差数字宣称完整风格一致。

反馈示例：“保留已通过的桃金开口和暗树干。把新增光从正面崖肩移到可见土苔顶面，按纹理打断，保持下方岩壁暗体；提交同机位全图、缩略图及局部对照。”

## 交付

提交分区 recipe、修改后的实际画面、相关版本与设备信息，以及仍未匹配的材质或构图差异。若任务只有配色，不附带改变玩法或发布站点。

奥日案例的可迁移经验：更有亮感可以来自少量有颜色的高光、正确的落点承光和保留的深暗框景，甚至不需要提高全图中位亮度。根据参考建立关系，比挑一组“好看”的 HEX 更可靠。
